# Чек на удачу — тестовое задание

Веб-приложение промо-акции: покупатель регистрирует чек, модератор проверяет.

## Стек

Python 3.12 · Django 5.0 · PostgreSQL 16 · Docker / Docker Compose · Vanilla JS

---

## Как запустить

### Через Docker (рекомендуется)

```bash
# 1. Клонируйте репозиторий
git clone <url> && cd receipt-promo

# 2. Создайте .env из примера
cp .env.example .env
# При необходимости отредактируйте .env (даты акции, секрет)

# 3. Поднимите сервисы
docker compose up --build

# 4. В отдельном терминале создайте суперпользователя (модератора)
docker compose exec web python manage.py createsuperuser
```

Сайт откроется на http://localhost:8000  
Админка: http://localhost:8000/admin/

### Локально (без Docker)

```bash
python -m venv venv && source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
# Укажите реальный DB_HOST=localhost в .env
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

### Запуск тестов

```bash
# В Docker
docker compose exec web python manage.py test receipts

# Локально
python manage.py test receipts
```

## Что реализовано

### Обязательная часть
- **Модель чека** — ФН, ФД, ФП, дата/время покупки, сумма, статус, причина отказа, пользователь, дата регистрации
- **Регистрация чека** — форма с серверной валидацией:
  - дата покупки входит в период акции (из `.env`)
  - сумма ≥ 1 000 ₽
  - уникальность ФН+ФД+ФП (повторный чек — понятная ошибка, не 500)
  - новый чек всегда в статусе «На проверке»
- **Личный кабинет** — список своих чеков, пагинация по 10, от новых к старым
- **Отправка формы через fetch** — успех и ошибка выглядят по-разному, без перезагрузки
- **Клиентская валидация** — обязательные поля, форматы, ошибки рядом с полями до отправки
- **Админка** — модератор меняет статус и указывает причину отказа
- **API** `GET /api/receipts/` — чеки текущего пользователя в JSON, чужие не отдаются
- **Docker** — `docker compose up --build` поднимает всё вместе с Postgres
- **`.env.example`** с датами акции

### Бонусные фичи
- **Поле «Вставить строку из QR-кода»** — парсит `t=...&s=...&fn=...&i=...&fp=...` и заполняет форму автоматически
- **Загрузка фото чека** — с проверкой формата (JPEG/PNG/WebP) и размера (≤ 5 МБ)
- **Статус обновляется без перезагрузки** — кабинет опрашивает `/receipts/status/<id>/` раз в 15 сек для чеков «На проверке»
- **Выгрузка принятых чеков в CSV** — действие в админке
- **Тесты валидации** — 12 тест-кейсов: сумма, границы дат, форматы ФН/ФД/ФП, дублирование, отклонённые чеки

## Спорные решения

### Дата акции и часовой пояс

Период акции сравнивается **только по дате** (без времени и таймзоны).  
Если на чеке написано «31 марта» — чек принимается, неважно, в каком часовом поясе покупатель.  
Альтернатива — хранить период как datetime с явной таймзоной — усложнила бы UX: пользователю пришлось бы знать, «по московскому или UTC?». При этом реальные акции всегда формулируются как «покупка с X по Y», имея в виду дату на чеке.

### Повторная подача отклонённого чека

Запрещена. Уникальность ФН+ФД+ФП обеспечивается на уровне БД (unique_together) и в форме.  
Причина: если чек отклонён (фрод, технический брак), возможность переподать открывает очевидный путь для злоупотребления. Если отклонение ошибочно — пользователь обращается в поддержку.  
Это решение описано в сообщении об ошибке: «Чек с такими реквизитами уже зарегистрирован (статус: Отклонён)».

### Авторизация API

Используется сессионная аутентификация Django — достаточно для браузерного клиента. JWT не вводился: задание не требует внешнего API-клиента, а добавление зависимости (DRF / PyJWT) усложнило бы проект без пользы.

## Работа с ИИ

**Где ИИ помог сильнее всего**  
Скаффолдинг: создание всей структуры файлов, шаблонного кода моделей/форм/вьюх и docker-compose — то, что при ручном написании занимает время, но не требует творческих решений.

**Что он выдал неправильно**  
Первоначально предложил добавить djangorestframework для единственного GET-эндпоинта. После анализа стало понятно, что это избыточная зависимость — заменил на обычный JsonResponse.

**Что переписал бы при наличии времени**  
Клиентский JavaScript в `register.js` — сейчас это одна большая IIFE. Разбил бы на отдельные модули (qr-parser, validator, form-submit), добавил бы TypeScript для надёжности типов.
